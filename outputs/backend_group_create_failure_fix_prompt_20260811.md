# BBchat 创建群聊失败：后端排查与修复 Prompt

你是 BBchat 后端项目的资深工程师。请直接在现有后端仓库中排查并修复 `POST /api/v1/groups/create` 创建群聊失败的问题，提交可运行代码、数据库迁移（如需要）、自动化测试和联调证据。不要只给分析或伪代码，不要用客户端本地假成功绕过后端失败。

## 已知客户端事实

当前 Expo/iOS 客户端创建群聊时发送：

```http
POST /api/v1/groups/create
Authorization: Bearer <access-token>
Accept: application/json
Content-Type: application/json
```

```json
{
  "name": "群聊名称",
  "member_ids": ["stable-user-id-1", "stable-user-id-2"],
  "is_public": false
}
```

成员来源是：

- `GET /api/v1/follows/following?page=1&limit=30` 中 `followed_by_me=true && follows_me=true` 的互关用户；
- `GET /api/v1/follows/followers?page=1&limit=30` 返回的粉丝，包括仅单向关注创建者的粉丝；
- `member_ids` 使用列表返回的稳定字符串 `user_id`，不使用 username、昵称或关注关系记录 ID。

客户端现已调整为：HTTP 非 2xx、HTTP 200 但响应数值/数字字符串 `code != 0`、解码失败、401、网络错误都会判定为创建失败，并向用户展示后端返回的可读错误消息。因此后端不能用 HTTP 200 + 非零业务码表达“部分成功”或静默失败；符号业务码必须配合明确的 HTTP 4xx。

## 第一阶段：必须先取得真实失败证据

1. 使用发生问题的真实账号和同一组 `member_ids` 重放一次请求；不要在未复现前猜测原因。
2. 贯穿记录并回传：`request_id`、认证用户 ID、HTTP 状态、响应 `code/message/data`、群名长度、`is_public`、成员数量，以及每个成员的资格判定结果。日志中不要记录 access token。
3. 检查 nginx/网关、应用服务、数据库事务三层日志，确认失败发生在鉴权、JSON 校验、用户查询、关系校验、群写入、群成员写入、初始会话/事件写入中的哪一步。
4. 检查是否存在以下高概率问题：
   - 创建接口仍强制要求传统好友，而选择页已经允许互关和仅关注创建者的粉丝；
   - 关注关系查询方向写反；正确资格条件是“候选成员关注了创建者”；
   - `user_id` 在列表接口是字符串，但创建接口错误地按数据库整数主键解析；
   - 粉丝在页面打开后取消关注、被拉黑、注销或封禁；
   - 群名长度、敏感词、公开群权限或人数上限被拒绝，但响应缺少稳定错误码；
   - 群记录已写入，但群成员、会话或初始事件写入失败，事务没有完整回滚；
   - 服务返回 HTTP 200 + 非零 `code`，导致旧客户端误判成功。

## 成员资格规则

创建者可添加满足以下任一条件的有效用户：

1. 候选用户与创建者互相关注；
2. 候选用户单向关注创建者，即候选用户是创建者的粉丝；
3. 为兼容旧客户端，如果历史好友可能不具备上述关注关系，采用“已接受好友 OR 候选用户关注创建者”的并集规则，并在交付说明中明确最终规则。

服务端必须基于数据库中的实时关系重新校验，不能信任客户端传入的关系字段。删除、注销、封禁、任一方向拉黑、禁止入群或违反安全策略的用户必须拒绝。`member_ids` 应去重；创建者本人只能出现一次。只要有一个成员无效，整个操作必须原子失败，不能静默跳过无效成员后创建残缺群。

## 接口响应要求

成功使用 HTTP 2xx 和统一响应包络：

```json
{
  "code": 0,
  "message": "ok",
  "data": {
    "group_id": 123
  }
}
```

`data` 可增加字段，但必须兼容仍按空 `data` 解码的旧 iOS 客户端。

业务失败使用明确的 HTTP 4xx，响应顶层必须始终有非空 `code` 和可直接展示的 `message`，并保留 `X-Request-ID`。例如：

```json
{
  "code": "GROUP_MEMBER_NOT_ELIGIBLE",
  "message": "部分成员已不在你的粉丝列表中",
  "data": {
    "invalid_member_ids": ["stable-user-id-2"]
  }
}
```

至少稳定区分：

- `GROUP_MEMBER_NOT_ELIGIBLE`：关注/好友资格不满足；
- `GROUP_MEMBER_NOT_FOUND`：用户不存在；
- `GROUP_MEMBER_BLOCKED`：存在拉黑或账号限制；
- `GROUP_MEMBER_LIMIT_EXCEEDED`：人数超限；
- `GROUP_NAME_INVALID`：空白、过长或敏感词；
- `GROUP_PUBLIC_NOT_ALLOWED`：当前账号无权创建公开群；
- `UNAUTHORIZED`：鉴权失败。

不得返回 HTML、空响应或只有嵌套 `detail` 而没有顶层 `message`。不得在 HTTP 2xx 中返回非零错误码。5xx 响应对客户端使用通用可读消息，具体异常和堆栈仅写入带 `request_id` 的服务端日志。

## 事务与一致性

在一个数据库事务中完成：

1. 创建群；
2. 创建者入群并成为 owner；
3. 写入去重后的成员；
4. 创建必要的会话、初始系统事件和成员索引；
5. 提交后再广播 WebSocket/推送事件。

任一步失败必须完整回滚，不能留下孤立群、部分成员、幽灵会话或只对创建者可见的群。确认群成员表存在 `(group_id, user_id)` 唯一约束，并检查现有脏数据。

## 必须补充的测试

1. 互关用户创建成功；
2. 仅单向关注创建者的粉丝创建成功；
3. 创建者只关注对方、但对方未关注创建者时，按最终兼容规则判定；
4. 传统好友但无关注关系的旧客户端请求按兼容规则成功；
5. 无关系、取消关注、双向拉黑、注销、封禁、无效 ID 分别返回稳定 4xx；
6. 字符串 `user_id` 能正确解析，不能误当整数数据库主键；
7. 重复成员和包含创建者本人时不会生成重复群成员；
8. 任一成员无效时原子失败且数据库无残留；
9. 群名为空、超长、敏感词，公开权限不足和人数超限的错误码正确；
10. 成功响应 `code=0`，所有失败响应 HTTP 非 2xx 且顶层 `message` 非空；
11. 创建后创建者与所有成员都能从 `GET /groups/list` 查到同一 `group_id`，并能读取群详情；
12. WebSocket/推送只在事务提交后发送，事务回滚时不得广播成功事件。
