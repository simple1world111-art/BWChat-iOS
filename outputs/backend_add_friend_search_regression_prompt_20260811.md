# BBchat 添加好友搜索结果回归：后端排查与修复 Prompt

你是 BBchat 后端项目的资深工程师。请直接在现有后端仓库中排查并修复 `GET /api/v1/friends/search?keyword=...`：同一账号使用同一关键词，之前能找到的有效用户现在返回空列表；尤其检查用户被关注后是否被错误地从搜索结果排除。请提交真实根因、可运行代码、自动化测试和联调证据，不要只输出分析或伪代码。

## 客户端契约

请求：

```http
GET /api/v1/friends/search?keyword=seven
Authorization: Bearer <access-token>
Accept: application/json
```

成功响应必须始终使用统一包络：

```json
{
  "code": 0,
  "message": "ok",
  "data": {
    "users": [
      {
        "user_id": "stable-user-id",
        "nickname": "小七",
        "avatar_url": "https://cdn.example/avatar.png",
        "relation": "none",
        "followed_by_me": true,
        "follow_requested": false
      }
    ]
  }
}
```

`data.users` 必须是数组；真实无匹配时返回空数组。不得改成顶层 `users`、`data.results`、裸数组、`null`，也不得用 HTTP 200 + 非零业务码表示失败。

## 必须先取得真实失败证据

1. 使用报告问题的账号、原关键词和目标用户复现，保存脱敏的 `request_id`、HTTP 状态、响应 `code/message/data`。
2. 在关注前、关注成功后、取消关注后分别执行同一搜索，比较查询条件和结果。
3. 检查网关、应用日志、搜索 SQL/ORM、缓存命中与缓存 key；日志不得记录 access token。
4. 确认问题属于哪一类：
   - 查询错误地排除了 `followed_by_me=true`、好友或已有会话用户；
   - 关注写入后没有失效搜索缓存，空结果覆盖了旧结果；
   - username/nickname 的大小写、Unicode、前后空白或分词规则发生变化；
   - 用户 ID 类型或 JOIN 方向错误；
   - 返回包络从 `data.users` 漂移；
   - 数据库读副本延迟或权限/拉黑过滤误判；
   - 500/超时被错误包装成 200 空列表。

## 目标语义

- 搜索范围包含未关注、已关注、关注请求中、互关和好友用户；只排除当前登录用户，以及按既有安全策略不可见的注销、封禁或拉黑目标。
- 已关注用户仍必须返回，只是 `followed_by_me=true`；不能因为“已经添加”就从结果中消失。
- 搜索用户名和昵称，沿用现有产品允许的用户 ID 搜索则继续支持；匹配应忽略首尾空白和大小写，并正确处理 Unicode。
- `followed_by_me`、`follow_requested`、`relation` 必须根据当前登录用户与目标用户的实时关系计算，不能使用目标用户自己的关系或反向 JOIN。
- 同一关键词、同一关系 revision 下结果必须稳定；关注状态变化只更新关系字段，不应让目标行消失。
- 后端请求失败必须返回明确的非 2xx JSON 错误和可读 `message`，不能降级成成功空数组。
- 如果使用搜索缓存，key 至少包含规范化关键词、当前用户 ID 和影响可见性的关系/权限版本；关注、取消关注、拉黑和账号状态变化后必须正确失效。

## 安全与性能

- 当前用户身份只能来自 JWT，不接受客户端传 owner ID。
- 不返回手机号、邮箱或其他非搜索公开字段。
- 保留现有频率限制、防枚举策略和结果数量上限，但限流必须返回稳定 429，不能返回 200 空数组。
- 审计 username/nickname 的索引和查询计划，避免为了兼容已关注用户而做无界全表扫描。

## 必须补充的测试

1. 未关注用户按 username、nickname 能搜索到。
2. 关注成功后使用相同关键词仍返回同一 `user_id`，且 `followed_by_me=true`。
3. 私密账号待审批时仍返回，且 `follow_requested=true`。
4. 互关、好友、已有空会话和已有消息会话均不会被错误排除。
5. 取消关注后目标仍可搜索，关系字段恢复正确。
6. 当前用户本人、注销、封禁和按既有规则拉黑的目标正确过滤。
7. 大小写、中文、日文、空格、特殊字符和 URL 编码关键词正确。
8. 两个账号使用同一关键词时关系字段和缓存完全隔离。
9. 数据库/缓存/依赖故障返回非 2xx 错误，不返回成功空列表。
10. 成功响应始终为 `{code,message,data:{users:[]}}`，每行必含稳定字符串 `user_id`。
11. 关注事务提交后立刻搜索不会读到永久空结果；如允许短暂读副本延迟，必须有 read-your-write 或缓存失效保证。
12. 重复请求与并发关注/搜索不产生随机缺行或重复用户。
