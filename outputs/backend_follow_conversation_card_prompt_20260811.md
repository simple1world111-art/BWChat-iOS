# BBchat 关注成功后空私聊卡片跨设备一致性：后端修复 Prompt

你是 BBchat 后端项目的资深工程师。请直接在现有后端仓库中排查并实现：用户通过 `POST /api/v1/follows/{target_user_id}` 成功关注后，即使双方尚无任何消息，当前用户的 `GET /api/v1/chat/conversations` 也必须返回该目标用户的空私聊卡片，并正确兼容置顶、隐藏、快照 revision、跨设备同步和后续首条消息。请提交可运行代码、迁移（如需要）、自动化测试和真实联调证据；不要只输出分析、接口建议或伪代码。

## 已确认的客户端现象与契约

- “消息 → 添加好友 → 搜索用户 → 关注”成功后，关注接口返回关系对象。
- 当前会话接口只返回已有服务端会话行时，尚无历史消息的被关注用户不会出现在消息页。
- Expo/iOS 客户端已增加本机即时空卡片和账号隔离缓存，解决返回页面时的即时体验；后端改造目标是保证换设备、重装、清缓存和多端同时在线时也一致。
- 私聊卡片稳定身份为 `dm:{target_user_id}`，不能使用昵称、username 或关注关系记录 ID。
- 待审批的私密账号关注请求不算关注成功：只有响应中 `followed_by_me=true` 后才应出现卡片。

客户端请求：

```http
POST /api/v1/follows/{target_user_id}
Authorization: Bearer <access-token>
Accept: application/json
Content-Type: application/json

{}
```

会话快照：

```http
GET /api/v1/chat/conversations
Authorization: Bearer <access-token>
Accept: application/json
```

空私聊行至少必须满足现有客户端模型：

```json
{
  "type": "dm",
  "id": "stable-target-user-id",
  "name": "对方当前昵称",
  "avatar_url": "https://cdn.example/avatar.png",
  "unread_count": 0,
  "is_muted": false,
  "is_pinned": false
}
```

没有消息时不要伪造 `last_message`、`last_message_time` 或 `last_message_id`。

## 必须先排查并给出根因证据

1. 使用两个真实测试账号复现：A 关注 B，双方无历史消息，记录关注响应与随后会话快照。
2. 记录脱敏的 `request_id`、A/B 稳定用户 ID、HTTP 状态、响应 `code/message/data`、会话快照 `revision` 和 `snapshot_complete`；不得记录 access token。
3. 定位 `GET /chat/conversations` 当前数据源：只聚合消息/会话摘要表，还是还会并入好友、关注和会话偏好。
4. 检查关注事务提交后是否更新会话可见性、快照 revision、缓存失效和账号级 WebSocket 刷新事件。
5. 检查置顶/隐藏表是否以 `(owner_user_id, conversation_type, target_id)` 唯一，并确认空私聊行是否错误地因没有最后消息而被过滤。

## 服务端目标语义

### 1. 关注成功必须物化“会话列表可见性”

当 `POST /follows/{target_user_id}` 最终返回 `followed_by_me=true` 时，在同一个事务中或通过具备可靠 outbox 的提交后流程，使当前用户的会话快照能够稳定包含 `dm:{target_user_id}`。

可以按现有架构选择以下一种实现，但必须说明选择与一致性保证：

- 在用户级会话索引/摘要表中 upsert 一条无最后消息的 DM 行；或
- 查询 `GET /chat/conversations` 时，将“确认关注关系”与已有会话索引做稳定并集；或
- 在现有用户级会话偏好/可见性表中物化该 DM 目标，再由会话查询联表返回。

不要创建伪消息，不要增加未读数，不要向对方制造一个虚假的收到消息事件。重复关注或重试必须幂等，不能生成重复会话行。

### 2. 置顶与隐藏规则

- 会话身份必须始终为 `(owner_user_id, dm, target_user_id)`。
- 如果该身份已有 `is_pinned=true`，关注成功和空卡片物化不得清除置顶；返回行必须继续带 `is_pinned=true`，并进入置顶区。
- 如果没有置顶，新空卡片必须位于全部置顶会话之后；普通区继续遵循项目现有稳定排序。
- 关注成功表示用户明确希望重新看到目标用户：如果该 DM 只有旧的隐藏标记，应清除当前用户的隐藏状态，但不得删除历史消息。
- 如果现有“隐藏会话”动作会自动取消置顶，继续保持该既有规则；不要在关注事务中无条件把 `is_pinned` 写成 `false`。
- 取消关注不应删除已有消息或会话历史。对于已物化的空卡片是否保留，请按当前产品会话语义审计后保持稳定；本需求建议保留，直到用户主动从消息列表删除，避免多端闪烁和本地状态反复。

### 3. 会话快照完整性

- `snapshot_complete=true` 时必须包含所有对当前用户可见的空关注 DM，不能只包含有消息的会话。
- 新增或恢复空 DM 后必须单调推进该用户的会话快照 `revision`，旧 revision 不能覆盖新状态。
- `total_unread_count` 不因空卡片变化。
- 昵称和头像从权威用户资料读取；资料变化后沿用现有会话资料刷新机制，不能永久复制陈旧值。
- 目标账号不存在、已注销、被封禁或双方存在阻止会话展示的安全关系时，按现有安全策略处理，并给出测试覆盖。

### 4. 实时与多端同步

关注事务提交后，向当前用户的其他在线设备发送现有的账号级会话刷新事件（例如客户端已支持的 `refresh_conversations`），或发送等价、稳定、可重放的会话 upsert 事件。事件必须在事务提交后发布，回滚时不得发布。

事件至少要让其他设备重新获取包含该空 DM 的新 revision；不要向被关注用户发送“新消息”或增加未读。

### 5. 首条消息衔接

之后任一方发送首条真实消息时，必须更新同一个 `dm:{target_user_id}` 会话行，而不是再创建第二条身份不同的会话。消息、会话摘要、未读、revision 与 outbox/WebSocket 必须保持现有事务和幂等保证。

## 兼容要求

- 沿用现有 JWT 鉴权、`{code,message,data}` 包络、错误码、数据库事务、缓存和日志脱敏规范。
- 不改变现有 Conversation 字段的类型；新增字段必须可选，旧客户端可忽略。
- 不要求客户端传 owner ID；owner 必须来自 access token。
- 不得使用 HTTP 200 + 非零业务码伪装失败。
- 不得通过创建系统消息、空字符串消息或未来时间戳来让卡片出现。

## 必须补充的自动化测试

1. A/B 无历史消息，A 关注 B 成功后，A 的会话快照出现唯一空 DM 行。
2. 私密账号仅返回 `follow_requested=true, followed_by_me=false` 时不出现；请求被接受、关系变为 `followed_by_me=true` 后出现。
3. 重复关注、客户端重试和两个并发关注请求只产生一条会话身份。
4. 空卡片 `unread_count=0`，没有伪造最后消息字段，`total_unread_count` 不变。
5. 已置顶 DM 在关注/重新关注后仍置顶；新未置顶 DM 排在所有置顶项之后。
6. 旧隐藏空 DM 在确认关注后重新可见，但历史消息不被删除。
7. `snapshot_complete=true` 包含空 DM；revision 单调递增，旧快照不能覆盖。
8. 关注提交后当前用户的另一在线设备收到刷新/upsert，并能拉到新卡片；被关注用户不增加未读。
9. 首条真实消息复用同一 DM 身份并正确更新预览、时间、消息 ID 和未读。
10. A 的卡片/置顶/隐藏状态不泄漏给 B 或其他账号。
11. 目标不存在、注销、封禁、拉黑等安全边界按现有规则返回稳定结果且不留下脏索引。
12. 取消关注不删除历史；最终空卡片保留/删除语义必须有明确测试并与产品规则一致。
