# 朋友圈“关注”Feed 后端改造 Prompt

请调整朋友圈关注 Feed，确保它只返回当前登录用户主动关注的账号所发布的动态。

## 目标接口

- 保持现有接口：`GET /api/v1/moments/feed`
- 鉴权：必须使用当前登录用户身份，不接受客户端传入任意 viewer user_id
- 分页参数：`limit`、`before_id`

## 必须满足的查询语义

1. 只返回 `follows.follower_id = current_user.id` 对应的 `followee_id` 作者动态。
2. 不返回当前用户自己的动态，除非产品的数据模型明确允许用户关注自己；默认应禁止关注自己。
3. 不混入推荐、热门、好友、互关、同城、运营置顶或广告内容。
4. 已取消关注、被拉黑、拉黑当前用户、账号已注销/封禁，或当前用户无权查看的私密动态必须排除。
5. 动态删除、作者可见性及屏蔽关系必须在查询时生效，不能只依赖异步缓存。
6. 按稳定的倒序游标分页；建议 `(created_at DESC, id DESC)`，`before_id` 必须能稳定定位下一页，不能重复或漏项。
7. `has_more` 表示过滤后的关注 Feed 是否还有下一页，不能使用过滤前候选集合计算。

## 响应格式

保持客户端现有契约：

```json
{
  "code": 0,
  "message": "ok",
  "data": {
    "moments": [],
    "has_more": false
  }
}
```

## 数据一致性

- 关注和取关成功后，后续新请求必须立即反映最新关系。
- 如果使用 Feed 缓存，缓存键至少包含当前用户 ID，并在关注、取关、拉黑、解除拉黑、作者封禁或动态权限变化时失效。
- 禁止不同用户之间复用未按 viewer 隔离的 Feed 缓存。

## 验收测试

请补充接口/集成测试，至少覆盖：

1. A 关注 B，未关注 C：Feed 只出现 B 的动态。
2. A 发布自己的动态：A 的关注 Feed 不出现该动态。
3. A 取关 B 后刷新：B 的动态立即消失。
4. A 一个账号都未关注：返回空数组且 `has_more = false`。
5. 某一候选页大部分内容因权限或拉黑被过滤：仍能正确继续查找后续可见内容，且游标无重复、无漏项。
6. B 设置私密或屏蔽 A：A 的 Feed 不出现 B 的受限动态。
7. 两个不同登录用户并发请求：响应和缓存不会串数据。

完成后请提供：变更文件清单、数据库查询/索引说明、缓存失效策略、接口测试结果，以及一组可供 iOS 联调的请求与响应示例。
