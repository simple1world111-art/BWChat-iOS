# 朋友圈发帖媒体互斥规则：后端改造 Prompt

请在后端实现并验证朋友圈（Moments）发帖媒体规则。目标是让服务端成为最终可信边界，不能只依赖 iOS 客户端限制。

## 业务规则

针对创建朋友圈接口（当前 iOS 调用 `POST /moments/create`，请按项目实际 API 前缀处理）：

1. 允许纯文字帖子，不上传任何媒体。
2. 有媒体时，一条帖子只能是以下两种形态之一：
   - 1～9 张图片；
   - 1 个视频。
3. 图片和视频不能混合上传。
4. 视频数量不能超过 1 个。
5. 图片数量不能超过 9 张。
6. 不允许静默截断、忽略多余文件或只保留第一种媒体；非法请求必须整体失败，不能创建半成品帖子。

## 接口与校验要求

- 保持当前 multipart 字段兼容：
  - `content`
  - 重复的 `media` 文件字段
  - `unlock_price_cat_food`（可选）
  - `client_request_id`（如当前已支持，继续用于幂等）
- 在写数据库和提交对象存储之前完成媒体集合校验；如上传框架必须先落临时文件，校验失败后要可靠清理全部临时文件。
- 媒体类型必须结合实际文件内容、可信 MIME 探测和允许的格式判断，不能只信任客户端传来的扩展名或 `Content-Type`。
- 对同一请求中的全部文件归一化为 `image` 或 `video` 后再执行集合校验。
- 校验失败建议返回 HTTP 422，并沿用项目现有响应 envelope。提供稳定的机器错误码（字段名按现有规范）：
  - `MOMENT_MEDIA_MIXED_TYPES`
  - `MOMENT_TOO_MANY_IMAGES`
  - `MOMENT_TOO_MANY_VIDEOS`
  - `MOMENT_UNSUPPORTED_MEDIA_TYPE`
- 错误信息应明确可展示，例如：
  - `一条动态不能同时包含图片和视频`
  - `最多只能上传 9 张图片`
  - `一次只能上传 1 个视频`
- 不要修改成功响应中现有的 `Moment` / `media` 数据结构。成功创建后，返回的 `media` 数组也必须满足“全图片或单视频”。
- 保持 `client_request_id` 的幂等语义：相同用户重复提交同一 ID 时，不得创建第二条帖子；并发重复请求也必须安全。
- 付费解锁字段只在帖子确实含媒体时生效；纯文字帖请忽略或拒绝正数 `unlock_price_cat_food`，行为需与现有产品约定一致并补测试。

## 数据层与历史数据

- 在 service/domain 层建立统一的 `MomentMediaPolicy`（或等价领域校验），所有创建入口、后台任务和管理端入口必须复用，避免只有某个 controller 生效。
- 如果数据库结构允许，增加能防止未来代码绕过的约束或事务内校验；不要用会破坏现有历史数据的迁移。
- 写一个只读审计脚本/查询，统计历史数据中：
  - 同帖混合图片和视频；
  - 同帖多个视频；
  - 同帖超过 9 张图片。
- 先输出审计结果和修复建议，不要自动删除或改写历史媒体。

## 必须覆盖的自动化测试

至少覆盖以下请求，并同时断言 HTTP 状态、业务错误码、没有创建帖子记录、没有遗留对象存储文件：

1. 纯文字：成功。
2. 1 张图片：成功。
3. 9 张图片：成功。
4. 10 张图片：422，`MOMENT_TOO_MANY_IMAGES`。
5. 1 个视频：成功。
6. 2 个视频：422，`MOMENT_TOO_MANY_VIDEOS`。
7. 1 张图片 + 1 个视频（两种排列顺序）：422，`MOMENT_MEDIA_MIXED_TYPES`。
8. 伪造扩展名或 MIME 的文件：按实际内容识别并拒绝不支持的媒体。
9. 同一 `client_request_id` 串行与并发重放：只创建一条帖子。
10. 校验失败或持久化失败时：数据库和对象存储均无半成品。
